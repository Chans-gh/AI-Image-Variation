## 0. 执行摘要

Image Variations Skill 将用户输入的 **单张参考图 / 文本 / 单张参考图+文本**，转换为围绕一个主体、一个变化方向生成的系列图片。支持两种完全独立的出图模式：

- **Grid Mode（网格图）**：2×2、3×3、4×4，**一次生图请求**生成一张完整、无缝、等格的作品板；第一阶段**必须**提供整图与自动切出的 N² 张单图。
- **Sequence Mode（连续出图）**：4–16 张，系统先生成一组按序且互不雷同的 **N 条独立提示词**，再生成 N 张独立图片；三种序列分支（离散变体 / 渐进演变 / 情节叙事）每次任务只选一种，不混合。

两种输出均支持原包的全部 12 个变化方向；用户单次任务只选一个方向。优先调用宿主提供的生图能力，或按用户配置调用 **GPT Image 兼容协议 / Gemini Nano Banana 兼容协议**；缺能力时明确报错，不静默降级。**[已确认]**

## 1. 产品目标、非目标与交付边界

### 1.1 产品目标（P0）

1. 用一套 Skill 指令入口统一完成参数解析、主体锚定、变化规划、提示词生成、模型调用和交付。
2. 保持主体身份/核心特征的稳定性；把差异明确限定在选中的一个变化方向内。
3. 网格图采用单次生成，后处理保证输出单图在**像素尺寸和比例上一致**，具备规则切图坐标。
4. 序列图每张图具有独立且有序的变化点；纯文本模式以首次生成的图 1 作为后续一致性锚点。
5. 支持可扩展的方向规则库、协议适配器和任务输出清单；提供透明错误及有限重试。

### 1.2 第一阶段明确不做

- 不修改、迁移或依赖原网站 `/tools/image-variations/`、原后端或鉴权系统。
- 不把「多方向混合」作为功能；不在单次任务中混合多种序列分支。
- 不支持 2×3、1×9 等非 NxN 网格；不支持超过 16 张的序列。
- 不自动生成小红书笔记、视频、动态 GIF、故事脚本或营销发布流程（原包的笔记生成属于历史参考，**不进入 Phase 1**）。
- 不承诺所有供应商均支持任意比例和 4K；不可用时返回可操作的错误。
- 不把网格生成改成先生成若干单图后拼接；**必须维持一次模型生成完整网格**。

### 1.3 架构假设

**[设计方案]** 采用 Agent Skills 风格的 `SKILL.md` + `references/` + `scripts/` 文件夹封装工作流。运行依赖宿主提供文件、图片模型、密钥保管及任务执行能力；如果宿主没有这些能力，需要另行接入运行适配器，Skill 文件本身不等于一个生图模型服务。该封装方案可更换，不影响本文业务规则。

## 2. 核心术语与约束优先级

| 术语 | 定义 |
| --- | --- |
| Subject / 主体 | 本任务中始终被识别为同一人、动物、产品、物件、空间或主题的核心对象。 |
| Consistency Anchor / 一致性锚点 | 原图或稳定主体设定；纯文本序列在图 1 出来后，图 1 成为实际图像锚点。 |
| Direction / 方向 | `state` 等 12 种之一；每任务**恰好一个**。 |
| Branch / 序列分支 | `variants`（离散变体）、`progression`（渐进演变）、`narrative`（情节叙事）；仅用于 Sequence。 |
| Grid Board / 作品板 | 单个模型输出文件，内含 N 行 N 列，后续确定性切分。 |
| Resolution Tier / 分辨率档位 | 产品层的 1K / 2K / 4K 质量/目标大小档位；**不等于固定的像素宽高**。 |
| Tile / 单格 | 网格板中的一个矩形单元，所有 Tile 具有完全相同的像素宽高。 |
| Provider Adapter / 模型适配器 | 将统一生成请求映射为特定服务商参数，并解析返回内容。 |

**优先级（从高到低）**：平台安全/模型政策与不可违反的接口能力 → 用户显式选择的模式、方向、张数、比例、档位、分支和主体限制 → Skill 的一致性与输出结构要求 → 方向规则的允许变/必须稳/禁止项 → 通用默认值 → 原始文本中的非结构化平台参数。用户在自由文本里明确写出的规格应被解析为产品参数；与已选结构化参数冲突时，结构化参数优先，必要时提示冲突。**[设计方案]**

> **变化规则覆盖原则**：主体**核心识别**始终不变；选中方向允许变化的非核心元素可以变化。例如 `styling` 允许换服饰，不能被通用的“服装保持不变”误锁；`style` 可以换美术风格，但不能换主体。Sequence 的分支规则可覆盖原包仅针对 Grid 的“不能连续动作/不必连续”限制。

## 3. 输入、参数与缺省规则

### 3.1 输入类型 [已确认]

1. **image_only**：一张 PNG/JPEG/WebP 参考图，可无文字；由图像理解生成基础主体设定。
2. **text_only**：仅有非空文本，先抽取并固定主体设定。
3. **image_plus_text**：一张图 + 文字；图像锁定主体，文字用于补充指定变化与允许的细节。

至少有一张图或有效文本；V1 仅接收**一张原图**，不支持多参考图的角色融合。**[设计方案：输入张数限制与原包一致]**

### 3.2 参数矩阵

| 参数 | Grid Mode | Sequence Mode | 状态 |
| --- | --- | --- | --- |
| `output_mode` | `grid` | `sequence` | [已确认] |
| `grid_size` | 2 / 3 / 4（对应 4/9/16 格） | 不适用 | [已确认] |
| `image_count` | N²（推导，不可单独设） | **4–16** 整数 | [已确认] |
| `direction` | 12 类之一 | 12 类之一 | [已确认] |
| `branch` | 不适用（离散网格） | 3 类中的一种 | [已确认：存在3种且不混合；代码命名是设计方案] |
| `aspect_ratio` | 有原图继承，无图 3:4 | 同左 | [已确认] |
| `resolution` | 2×2→1K；3×3→2K；4×4→4K | 默认 1K | [已确认] |
| 分辨率覆盖 | 可指定 1K/2K/4K | 可指定 1K/2K/4K | [已确认] |
| 图像输出 | 一张网格板 + N² 张自动切图 | N 张独立图片 | [已确认] |
| 二次打包 | 支持整板与切图打包 | 支持序列打包 | [已确认] |
| 模型来源 | 内置/用户配置 | 内置/用户配置 | [已确认] |

**[设计方案：未显式指定时的启动默认]** `output_mode=grid`、`grid_size=3`、`direction=state`、`image_count=4`（仅 sequence）、`branch=所选方向的默认偏向`。这几个启动默认是方便自动化的**建议**，不同于用户已确认的「网格档位映射、文本默认 3:4、序列默认 1K」。

### 3.3 比例继承

- 有图：读取已纠正 EXIF 朝向后的原图 **宽/高**，作为目标单图比例与整张 NxN 网格板比例；用户明确要求新比例时以其为准。
- 无图：默认 **3:4**；若明确指定其他比例，用显式比例。
- 不得为了适配模型**悄悄裁剪主体、改变比例或换档位**。不支持该比例时在调用前报 `UNSUPPORTED_RATIO`，说明模型能力和可选的替代比例。
- **[设计方案]** 比例以宽:高表示，支持规范化如 `3:4`、`4:3`、`1:1`、`16:9`、`9:16`；其他比例在对应模型支持精确尺寸时可以使用。模型返回比例必须实测；误差超阈值不得冒充满足规格。

### 3.4 分辨率语义（必须避免误读）

- **Grid 的 1K / 2K / 4K 指完整作品板的请求档位**，不能宣称每格分别具有 1K / 2K / 4K。
- **Sequence 的 1K / 2K / 4K 指每张独立图片的请求档位**。
- Adapter 负责把档位翻译为服务商的 `size`、`imageSize`、`quality` 等实际字段；`requested_resolution` 与 `actual_width/height` 都记录在结果里。
- 不允许把「1K」武断固定成 1024×1024，也不允许承诺两个模型的 4K 输出像素完全相同。模型支持能力先查询/声明，再做生成前校验。

### 3.4.1 分辨率档位最终决策（已确认：2026-11-17）

**采用 A：模型原生分辨率档位（Provider-Native Resolution）**。产品层的 `1K`、`2K`、`4K` 是请求所选模型原生能力的档位标识；**不是跨模型统一的像素边长、最小像素门槛或图片增强指令**。不支持目标档位即报错，不允许默默降低档位或用放大图伪称原生高分辨率。

- Grid：2×2 默认整板 `1K`，3×3 默认整板 `2K`，4×4 默认整板 `4K`；用户可覆盖。各格是整板切图，**不继承整板档位声明**。
- Sequence：4–16 张，默认每张原生 `1K`；用户可选 `2K`/`4K`；所有帧共享同一请求档位。
- Gemini 对已验证支持档位的型号按**真实 API 路由**发送 `imageSize` / `image_size` 等原生参数。GPT Image 对没有官方 K 档位字段的型号，由**经版本化验证的能力档案**把产品档位映射为受该型号支持的原生 `size=WIDTHxHEIGHT`；其 `quality` 不代表分辨率档位。
- 禁止在无法证明档位能力时仅以 `size=auto` 或 `quality=high` 充当所请求的 `2K`/`4K`。不支持或能力未知则在付费调用前报错，给出用户可选的调整建议；**不自动切换模型/比例/档位**。
- 生成后读取**原始返回图**的真实像素，记录原生档位的请求方式、真实像素及验证结果；网格几何规范化属于衍生后处理，不得改变原生输出的历史记录。

**规范性细则与错误码以第 17 章为准；第 17 章对第 3、7、8、9、10、13、16 章的尺寸处理具有补充和解释优先权。**

## 4. 用户工作流及路由

### 4.1 交互主链

```text
用户输入 → 识别输入类型 → 解析显式要求与默认参数 → 校验模型能力
        → 构建主体锚点 → 选择唯一方向 → 制定变化计划
        ├─ Grid：N² 个格位变化点 → 一条完整网格 Prompt → 一次生成网格板
        │        → 验证网格 → 规范化边长 → 自动切出 N² 张 → 返回/打包
        └─ Sequence：一个分支、N 个有序变化点 → N 条独立 Prompt
                 → 生成图 1（无图时建立锚点） → 其余按图 1 / 原图锚定
                 → 逐张验证 → 返回有序图片组 → 按需打包
```

### 4.2 指令识别 [设计方案]

- “3×3 网格、九宫格” → `grid_size=3`；“连续输出 9 张、九张独立图片” → `sequence,image_count=9`。
- 仅说“九张”而无法判断拼板还是独立文件时，优先询问一次，不擅自把 9 张解释为九宫格。
- 指定“按动作推进/逐渐变亮/一个故事的分镜”分别优先解析为 `progression` / `progression` / `narrative`；未指定时取方向默认分支。
- 用户选择多个主方向时提示只可选一个；**不自动混用**。不应仅因文本中提到“摄影+雨天”等自然描述，就认定用户选择了两个变化方向；自然描述可作为固定背景约束。

### 4.3 提交与进度 [设计方案]

创建任务后返回 `job_id`，支持 `queued → planning → generating → validating → postprocessing → completed`；失败使用 `failed`，序列有可用部分结果而仍有失败项时为 `partial_failed`。长任务展示 `completed_count / total_count`、每张生成状态和失败原因。缺模型能力或缺 Key 应在实际生成前同步发现。

**[已确认：v1.1 新增联动规则]** 仅在图片生成、验证、Grid 自动切图（如适用）和结果 Manifest 全部成功后，可以在结果交付时**推荐一次**继续使用 `Image Content Publishing Skill` 生成公众号文章或小红书笔记。推荐动作**不得创建内容任务、执行研究或产生第二阶段模型调用**；用户主动选择后才调用第二个独立 Skill。若用户明确只要图片，不反复推荐；若网格校验/切图未通过、序列部分失败，则默认不做“完整内容生产”推荐。历史产物可以在后续单独触发第二阶段。

### 5.1 Sequence 的三种分支

| 分支 | 目标 | 排列逻辑 | 检查重点 |
| --- | --- | --- | --- |
| `variants` 离散变体 | 同一主题下的 N 个独立且明显不同方案 | 变化点覆盖面最大化，不要求因果顺序 | 差异显著、不重复、不换主体 |
| `progression` 渐进演变 | 让一个可控指标逐步变化 | 起点→过渡→终点，阶段顺序明确 | 阶段单调/合理、连续、跨度足够 |
| `narrative` 情节叙事 | 同一世界观中的有序情节/分镜 | 起因→发展→转折→结果（按 N 扩展） | 人物/物品关系、空间/动作逻辑连贯 |

**[已确认]** 所有 12 方向在 Sequence 下均可使用这 3 个分支；每个任务只选**一个**分支。不存在「情节方向才能叙事」或「风格方向不能渐进」的硬限制。

**[设计方案：各方向的默认偏向，可配置]**：`state=variants`、`view=variants`、`scene=variants`、`detail=progression`、`light=variants`、`composition=variants`、`style=variants`、`styling=variants`、`weather=progression`、`lens=variants`、`usage=variants`、`narrative=narrative`。用户明确选择另一分支时准许覆盖，不混合。

### 5.2 分支在非典型方向中的应用示例

- `style + progression`：同一主体从写实到逐步加强的插画化，不是一开始就随机切换 16 种互不相关的风格。
- `view + narrative`：故事推进主要由镜头顺序表达，环境、服饰、事件保持统一，不能悄悄变成 `scene` 方向。
- `light + narrative`：一个事件中的光照情绪层次推进，但主变化仍是光影，不用引入全新的场景。
- `narrative + variants`：来自同一故事世界的多个独立片段，允许非线性，保持核心角色与世界观。

## 6. 主体一致性与文本归一化

### 6.1 主体设定

- 人物/动物：身份、脸型五官、发型外轮廓、体态、年龄感、识别性特征（不得在未要求时替换身份）。
- 产品/物件：核心外形、比例、材质识别、品牌感、关键部件；方向允许的包装/陈列等可变化。
- 空间/场景：空间布局逻辑、主视觉元素、色彩体系、世界观/整体美术方向。
- 用户明示的外观要求优先进入 `identity_anchor`；模型补足的缺失属性必须形成单一稳定设定，不能每图重抽。

### 6.2 有图场景

将原图作为全组稳定视觉基准，每次独立生图请求都携带原图（若适配器支持的图像编辑/参考图输入）。不得通过“前一张图→后一张图”的默认接力造成漂移。明确需要阶段推进时通过**变化计划/文字**控制顺序，而不是替换主锚点。**[已确认：保持统一锚点；具体请求组织是设计方案]**

### 6.3 纯文本 Grid

归一化描述（需要时）→ 构建稳定的文本身份锚点 → 单条 Grid Prompt 中要求所有 N² 格共享统一主体设定。无原图时不先生成单图，也不为网格拆分单独请求。**[已确认]**

### 6.4 纯文本 Sequence

1. 首先使用固定的 `identity_anchor + frame_01_change` 生成第 1 张；第 1 张同时是**序列的第一张结果**，不得作为额外隐藏的第 0 张。
2. 校验图 1 有效后，将图 1 设为 `anchor_image`；图 2–N 全部引用图 1，而不是图 i−1。
3. 每张 Prompt 都携带相同的 `identity_anchor`、统一世界观与对应 `frame_change`。若 `branch=progression/narrative`，加入阶段摘要确保前后关系。
4. 图 1 失败：不能继续；按重试策略重生图 1。图 i 失败：保留既有成功图，允许针对 i 补生成。
5. 若所选模型不支持参考图输入：**预校验报 `REFERENCE_REQUIRED`**，不得悄悄把后续帧降级成独立文生图。

> 这样“以第一张图为一致性”既是用户确认的业务规则，也是 Sequence 纯文本模式的硬性能力要求。

### 6.5 输入归一化 [设计方案]

参考旧包的 `normalized_prompt`、`subject_type`、`subject`、`identity_anchor`、`scene`、`style`、`lighting`、`composition`、`quality`、`keep_stable`、`discarded` 字段。对于明显冗长或含别家模型语法的纯文本输入，尝试调用宿主文本模型归一化；保留原文与归一化输出，使用 JSON schema 检验；解析失败不静默清掉用户的必要内容。简单输入可直接提取。不得把用户的 3:4 等有效显式需求当作应忽略的垃圾参数；应先解析结构化需求，再清理生图平台语法。

## 7. Grid Mode：生成、无缝网格与自动切图

### 7.1 单次生成要求 [已确认]

1. 生成前先计划 N² 个不重复主变化点，按**从左到右、从上到下**依次关联画格。
2. 在**一条**生成 Prompt 中同时表达网格总规模、主锚点、每格变化点、方向规则、禁止内容与目标比例；模型调用 `n=1`（语义上的单个最终输出）。
3. 完整输出必须为单张规则 NxN 网格图，不是 N² 张模型输出，也不是先分别生成再拼接。
4. **无缝**在本 SPEC 中指：**零可见间距、零边框、零衬底、零投影、零序号标签；画格尺寸统一且边界可按坐标直接切分**。画格内容各自完整，主体不得跨格。这条**覆盖**原包“纤细白色间距”的旧约束。
5. 格内独立比例 = 整张网格板比例（因为 N×N 且等格）；不得生成每格 3:4 却让整体成为 1:1 的拼贴版。

### 7.2 尺寸整齐性与像素规范化

- 设网格输出宽高为 `W,H`，要进行均匀无损几何切割，必须有 `W % N == 0` 与 `H % N == 0`；各格为 `tileW=W/N`、`tileH=H/N`。
- **[设计方案]** 当模型输出边长不整除 N，但画板结构/边缘检查通过时，可通过**极小幅的整图重采样**调整到最近的 `N` 倍数，单轴调整幅度不得超过原边长的 1%；同时检验比例误差不超过 1%。记录原始/规范化尺寸；禁止以裁剪画格中的主体来凑数。
- 当明显网格线偏移、某格空缺、跨格、出现厚边/白缝、总行列数错误时：**重采样并不能修复内容结构**，必须视为质量失败并有限重试，不允许假装切图成功。
- 所有自动切图必须**使用规范化后单张网格板的确定性整数边界**，输出第 `row* N+col +1` 张。保证格子的**像素宽高完全相同**；与目标比例的允许误差必须被记录且不得高于阈值。
- 只允许保真重采样进行几何规格对齐；不得通过拉伸明显错误比例来“满足”用户比例。

### 7.3 网格品质检查（P0）

**硬条件**：NxN 结构、N² 个可识别画格、无框无缝、无遮挡跨格、分割区域均等、输出图像可解码、真实比例满足容差。**语义检查**：所有画格主体一致、对应方向差异显著、无大面积重复、无文字/UI/水印等意外元素。

**[设计方案]** 采用两级验证：①确定性像素/尺寸/切图检验；②可用图像理解模型时进行语义视觉核验。最多进行 **2 次额外整板重试**（即总计最多 3 次网格生成请求，参数可配置）。若最终无法通过硬条件，返回 `GRID_VALIDATION_FAILED`，不把不合格文件标为合格切图。视觉一致性属于概率性评价，SPEC 约定验证与失败处理，不声称单次模型出图能数学保证完美结构。

### 7.4 Grid 返回物

- `grid_board.png`：最终合格的完整网格图。
- `tiles/01.png` … `tiles/NN.png`：按行优先的 N² 张自动切图。
- `manifest.json`：模式、方向、模型、档位、实际像素、切图坐标、验证结果、提示词版本等元数据。
- 用户可请求 `.zip` 二次打包；包内保留原作品板、切图、清单。**[设计方案：具体文件名/格式]**

## 8. Sequence Mode：分支规划与逐张提示词

### 8.1 计划必须先于模型调用

`SequencePlanner` 在调用图像模型前产出一个包含 N 个 `FramePlan` 的结构化计划，每个 `FramePlan` 至少包含：`index`、`change_point`、`visual_description`、`locked_elements`、`phase_label`（分支需要时）、`prompt`。全组的 `direction`、`branch`、`identity_anchor` 保持唯一。

### 8.2 生成规则 [已确认 + 实现方案]

- 单次任务只允许一种 `direction` 与一种 `branch`；`N ∈ [4,16]`。
- **N 条独立提示词**，每张图 `n=1` 的独立出图请求；不能只用同一个 Prompt 调 N 次，也不能通过一次 API 的 `n=N` 取巧代替差异化规划。
- `variants`：N 个离散不重复点，覆盖强弱层次；输出有索引顺序但不要求因果关系。
- `progression`：先定义单一主变量的阶段轴；N 个节点由起点渐进到终点，不允许大幅跳变又回退，除非用户明确要求往返过程。
- `narrative`：定义同一故事世界内的 N 个关键时刻；前后动作、物品、空间、服装等需可解释地连续，不能每张另起一个故事。
- 序列的统一画幅比例、分辨率目标和主体锚点在所有 N 张图上一致；实际像素必须分别记录，必要时仅在允许的轻微阈值内对齐，不得静默改变比例。
- 独立的每张生成失败时有限重试；保留成功图，最终返回完整成功或部分失败，不伪造成功数量。

### 8.3 Prompt 的共用与差异部分

每张图由下面的逻辑组件组装：

```text
GLOBAL_RULES（主体核心识别 + 单方向 + 禁止换主体 + 画幅/档位目标）
+ IDENTITY_ANCHOR（原图描述或图 1 锚点描述）
+ DIRECTION_RULES（允许变、必须稳、避免；当前唯一方向）
+ BRANCH_RULES（variants / progression / narrative 其中之一）
+ FRAME_PLAN[i]（第 i 张独有的主变化点与画面目标）
+ ORDER_CONTEXT（阶段摘要，仅用于 progression / narrative）
+ OUTPUT_RULES（单张成图，不要编号、分镜边框、UI或水印）
```

禁止把 `FramePlan[i]` 的变化点复制成完全相同的 N 条 Prompt。模型拒绝某一帧时记录实际错误，保持它在序列中的原索引，以便补生成。

### 8.4 结果呈现与打包

返回一个**有序图片列表**，每张具备稳定索引、可单独下载、可查看是否通过验证；可打包输出 `sequence/01.png…N.png + manifest.json` 的 zip。失败帧保留槽位信息，不能让后续序号前移而导致故事顺序错乱。

## 9. Provider Adapter 与用户配置模型

### 9.1 两类来源 [已确认]

- `builtin`：宿主已有的生图工具。使用宿主工具原生参数及认证；缺少工具时返回 `BUILTIN_UNAVAILABLE`。
- `external`：用户填写兼容类型、接口地址、API Key、模型 ID；Skill 通过适配器调用并解析结果。首批协议为 `openai_image_compatible`、`gemini_image_compatible`。

### 9.2 能力抽象

`ModelCapability` 至少包含：`text_to_image`、`reference_image_input`、`image_edit`、`supported_ratios`、`supported_resolution_tiers`、`custom_dimensions`、`supports_async_result`、`max_input_bytes`、`response_image_formats`。能力信息来自适配器已知声明和连接/预检；不能仅因为接口叫“OpenAI compatible”就假定所有 GPT Image 参数均支持。

**必须检查**：纯文本 Sequence 要求能接受图 1 作为参考的接口；图生图要求参考图能力；Grid/Sequence 选定比例、档位必须可表达。不满足则返回 `MODEL_CAPABILITY_UNSUPPORTED` / `REFERENCE_REQUIRED` / `UNSUPPORTED_RATIO` / `UNSUPPORTED_RESOLUTION`，**不自动静默降级**。**[已确认]**

### 9.3 GPT Image 兼容适配器

- 使用对应实现的**图像生成**和**图像编辑/参考图**路由；对于官方 API，其调用及参数随模型不同而不同。参考图输入不能被强行假设为所有供应商均支持 `image_urls` JSON 字段。
- 将统一的 `prompt`、实际目标尺寸、参考图片、格式等映射到该服务支持的字段；保存服务响应图片字节或授权访问的 URL，支持 base64 结果解码。
- GPT Image 服务的 `size` 可能采用宽×高字符串且与质量 `quality` 独立；`1K/2K/4K` 不等同于一个通用的官方 `resolution` 参数。

### 9.4 Gemini Nano Banana 兼容适配器

- 使用 Gemini 的原生图片生成/编辑接口、文本与图片输入结构，支持其当前 API 形态（例如 `generateContent` / 新版 `interactions`，由适配器版本声明决定）。
- 将 `aspect_ratio`、`image_size` / `imageSize` 等转换到选定 Gemini API 的真实字段；从模型返回的图像 part 中解析图片字节。
- Nano Banana 是**模型族**而非单个固定型号；模型能力、4K 与可选比例依具体模型版本判定，不绑定过时模型名。

### 9.5 配置、安全与失败策略 [设计方案]

用户配置建议字段：`provider_type`、`base_url`、`api_key_secret_ref`、`model_id`、`request_timeout_sec`、`capability_override`（仅管理员/开发环境）。连接测试只验证配置和权限，不触发无谓的正式批量生成。

- **API Key 不入提示词、不写进 Skill 包、不回显到日志/manifest/zip、不出现在 URL 参数中**；需要持久化时使用宿主密钥库加密，用户可更新/删除。
- 对自定义 Endpoint 仅允许 HTTPS，阻止内网、环回、元数据地址和重定向到内网的 SSRF；统一校验可访问目标及证书。
- 不把用户原图发送给未选定模型供应商；界面/任务结果明确所用 Provider 和模型，不记录 API Key。
- 第三方 HTTP 401/403 报鉴权错误，429 或网络超时可**有限重试**并遵循退避/`Retry-After`；参数不支持和安全拒绝不重试为同类请求，更不可自动换 Provider。
- 每个独立生成单元最大 **2 次额外重试**（设计默认，可配置）；生成次数与实际调用/成本需可观测。

### 9.6 协议参考（开发时以官方文档/选定模型最新能力为准）

- OpenAI Image Generation: https://developers.openai.com/api/docs/guides/image-generation
- OpenAI Image API Reference: https://developers.openai.com/api/reference/go/resources/images/methods/edit
- Gemini Image Generation: https://ai.google.dev/gemini-api/docs/image-generation
- Gemini Generate Content Image Config: https://ai.google.dev/api/generate-content

**注意**：这里约定“支持两类兼容协议”的**接口适配能力**，不表示第三方自称兼容就必然支持所有官方字段；具体端点、模型名、参数大小写与返回结构应由 Provider Adapter 版本锁定并在集成测试中验证。

## 12. 错误码与恢复策略

| 错误码 | 触发条件 | 用户可见处理 |
| --- | --- | --- |
| `INVALID_INPUT` | 无图无文、格式损坏或非法参数 | 解释缺失/错误字段，不调用模型 |
| `INVALID_MODE_OR_COUNT` | 非 2/3/4 网格或序列不在 4–16 | 显示允许区间 |
| `MULTIPLE_DIRECTIONS` | 同一任务显式要求多个方向 | 请只选择其中一项 |
| `UNSUPPORTED_RATIO` | 模型无法满足有效比例 | 显示支持比例，不静默裁剪 |
| `UNSUPPORTED_RESOLUTION` | 模型不支持指定档位 | 显示可用档位，不静默降档 |
| `REFERENCE_REQUIRED` | 当前任务必须以图为锚点、模型却不支持参考图 | 明确提示换兼容模型 |
| `AUTH_FAILED` | 用户 Key 无效/无权限 | 提醒检查配置，不回显 Key |
| `MODEL_CAPABILITY_UNSUPPORTED` | 其他必需能力不可用 | 标明缺失能力 |
| `RATE_LIMITED` / `PROVIDER_TIMEOUT` | 429、超时 | 有限退避重试，失败后可针对失败项重跑 |
| `GRID_VALIDATION_FAILED` | 整板不满足 NxN/无缝/可切图 | 有限重试后失败，不输出“已通过”切图 |
| `SEQUENCE_ANCHOR_FAILED` | 纯文本序列第一张失败 | 停止后续张数，支持重试第一张 |
| `IMAGE_VALIDATION_FAILED` | 单图损坏/比例异常/主体明显偏移 | 重试该张，最终可部分失败 |
| `MODEL_REFUSAL` | 模型拒绝或安全策略禁止 | 明确展示拒绝，不通过改 Provider 绕过 |

### 16.14 提示词组装与冲突处理（规范性）

1. 所有上游计划 Prompt 必须返回可解析的严格 JSON；渲染图像 Prompt 不需要模型返回 JSON，只需要图像。不要将长篇 JSON 的花括号字段作为不受控制的自由文本；占位符须做字符转义和长度/字段校验。
2. 在同一画面中 `{{DIRECTION_RULE}}` 不得与 `{{BRANCH_RULE}}` 产生冲突。**核心识别不变 > 当前方向允许变化 > 分支控制时间/排序方式 > 默认修饰**。举例：`styling + progression` 允许穿搭渐变，不能再要求“服装全部固定”；`narrative + variants` 是同故事世界的独立片段，不能强制连续动作拆帧。
3. 输入若有参考图但目标模型不支持图片输入，**阻断**而不是自动转成文字重生；纯文本 Sequence 首帧后必须支持以图1为参考。图像模型的输出可能改写提示词，实际请求与返回版本均记录在 Manifest；无法获知服务商内部重写时只记录自己发送的版本。
4. 网格“无缝”“等格”“等比例”是**结果验收条件**，不是模板文本出现过这些词就算完成。验证失败有限重试，未通过不交付合格切图。
5. 正常运行可以将本章节抽取到 `prompts/`，但**正文仍是规范性源**；修改运行模板应同步更新本 SPEC 的版本和回归测试。

## 17. 模型原生分辨率：尺寸规划、适配及验收（v1.3 规范性新增）

> **决策状态**：[用户已确认 2026-11-17] 选择 A「模型原生分辨率档位」。以下 P0 约束属于 Skill 01 正式规范，不是讨论建议。标记为「设计默认」的数值与容差仍需真实模型测试后冻结。第 16 章完整 Prompt System 继续全部有效；本章处理的是模型调用与机器验收，不能通过“提示词里写了 4K”代替。

### 17.1 术语与绝对原则

| 术语 | 含义及不可混淆之处 |
| --- | --- |
| `resolution_tier` | 用户选择的产品档位 `1K/2K/4K`，对应所选型号**经确认可调用**的原生分辨率能力。**不表示各厂商统一像素值**。 |
| `native_tier` | 模型在所用 API 路由中明确提供的分辨率档位参数，例如 Gemini 某些型号的 `imageSize`。 |
| `verified_native_size_mapping` | GPT Image 等没有官方 K 档位参数时，某个精确型号 + 路由经过版本化验证的 `1K/2K/4K` → 原生 `size=WIDTHxHEIGHT` 映射。属于**Skill 产品层分组**，不得冒称该提供方存在官方 `4K` 枚举参数。 |
| `actual_native_dimensions` | 服务端原始返回图片解码得到的 `width`、`height`，尚未经过本地重采样、裁切或放大。 |
| `effective_dimensions` | 图片通过允许的轻微几何规范化后实际用于展示 / 切图的尺寸。不能替代原生尺寸。 |
| `image_quality` | 供应商单独支持的质量、压缩或渲染强度选项，**不等于分辨率档位**。 |

**P0 硬规则：**

1. Grid 的档位只作用于**一次生成的整个网格作品板**；2×2→1K、3×3→2K、4×4→4K 是默认映射，不是每个 Tile 的分辨率承诺。
2. Sequence 的档位作用于**每张**独立生成图片；默认 1K；请求 4K 时必须按该型号原生 4K 能力/已验证映射对每张独立请求。
3. 不自动降级至更低档位，不自动切换模型，不自动更改用户指定或继承的目标比例；不通过普通放大、超分或重采样伪称达到了模型原生 4K。
4. 执行层必须分别记录 `requested_resolution_tier`、`provider_request`（排除鉴权秘密）、`actual_native_dimensions`、`effective_dimensions`、`resolution_validation`。
5. 如果型号能力档案未知、不足或不可信，则显示「该模型的目标原生档位尚未验证 / 不支持」并终止该请求；不得为了凑结果依赖 `auto` 随机尺寸后再声称成功。
6. 后处理允许在第 7.2 节既定容差范围内为 Grid 对齐画格整数坐标；这只是可切图几何修正，**不是原生分辨率补偿**。

### 17.2 Dimension Planner：输入、决策与输出

Dimension Planner 在第一次生图调用**之前**确定 `DimensionPlan`，由确定性代码完成，不交给语言模型或图像提示词决策。

**输入契约：** `output_mode`、`grid_size` 或 `image_count`、`requested_aspect_ratio`（用户指定，或原图 EXIF 归正后继承，或纯文本默认 3:4）、`resolution_tier`、`provider`、`model_id`、`api_route`、`capability_profile_version`。已确定的张数和方向规则继续由原有 Task Planner 负责。

**决策次序：**

1. 确定作用范围：Grid = 1 张 Board；Sequence = N 张 Frame。
2. 应用档位默认值与用户覆盖：Grid 为 `2→1K, 3→2K, 4→4K`；Sequence 为 `1K`，并验证 `4≤N≤16`。
3. 求出精确逻辑目标比例 `target_ratio = width / height`；**不**将模型的输出像素取整误差当作用户改变比例。
4. 使用精确的 `provider + model_id + api_route + capability_profile_version` 查询可用档位、比例、参考图能力以及参数映射。
5. 档位和目标比例均具备**有效的原生表达方式**才生成请求计划，否则中止并返回可操作错误。支持比例列表的型号使用真实比例选项；支持自定义尺寸的型号使用已验证的原生尺寸映射。
6. 输出严格结构化的 `DimensionPlan`；仅当状态 `ready` 时才能调用图像模型。

**规范性 `DimensionPlan` 关键字段：**

```json
{
  "dimension_policy": "provider_native",
  "scope": "board",
  "requested_resolution_tier": "4K",
  "requested_aspect_ratio": "3:4",
  "provider": "gemini",
  "model_id": "MODEL_ID_FROM_USER_CONFIG",
  "api_route": "interactions",
  "capability_profile_version": "PROFILE_REVISION",
  "mapping_kind": "native_tier_parameter",
  "provider_parameters": {
    "image_size": "4K",
    "aspect_ratio": "3:4"
  },
  "expected_native_dimensions": null,
  "generation_units": 1,
  "status": "ready"
}
```

此 JSON 为**形状示意**；`MODEL_ID_FROM_USER_CONFIG` 与 `PROFILE_REVISION` 是待填值，**不是已验证模型配置**。真实 Provider 参数由对应版本的适配器决定。`expected_native_dimensions=null` 表示不能把一个平台统一像素数强加给模型；若能力档案提供确定尺寸，应填写该模型支持的真实像素预期。

### 17.3 Provider Capability Profile：精确到型号与路由

能力档案至少包含：

- `provider_type`、`model_id`、`api_route`、`profile_version`、`source_url` / `verified_at`。
- `supported_native_tiers`：可请求的 `1K/2K/4K` 及其**原生实现类型**。
- `supported_aspect_ratios` / `custom_dimension_rules` / `reference_image_input`。
- `tier_map`：**每一档位**对应所用路由的有效参数或受支持的 `WIDTHxHEIGHT` 映射规则。支持自定义尺寸并不代表可自动宣称支持任意档位。
- `expected_output_dimensions_by_ratio`（官方有表则保存）、`output_tolerance_policy`、`notes`。

**分 Provider 映射规范：**

| 适配器 | 具备有效能力档案时的行为 | 禁止行为 |
| --- | --- | --- |
| Gemini 官方兼容 | 对支持分辨率枚举的具体型号，在 `generateContent` 中使用当前 API 的 `imageConfig.imageSize` / `aspectRatio` 或在 `interactions` 中使用 `response_format.image_size` / `aspect_ratio`；通过型号能力档案限制选项 | 把所有 Nano Banana 型号都视为支持 4K；忽略字段大小写或在路由间随意复用参数 |
| GPT Image 官方兼容 | 对没有官方 K 枚举的型号，在其**当前图像 API 路由**中用经验证的 `size=WIDTHxHEIGHT` 映射本产品档位；按照当前官方限制校验边长、宽高比及像素预算 | 将 `quality=high`、`auto`、压缩质量或后处理放大视为原生 4K；认为所有 GPT Image 型号有相同尺寸范围 |
| WorkBuddy 宿主内置生图工具 | 先读取或声明宿主工具/型号在当前版本可证实的分辨率能力，再映射原生档位 | 仅因工具可以生成图片，就默认其 4K 可用 |
| 自定义第三方兼容接口 | 按其**实际通过校验**的路由和型号能力档案执行，兼容格式仅用于请求结构，不保证能力对等 | 因名称包含 `OpenAI compatible` / `Gemini compatible` 就推断参考图、自定义比例或全部档位受支持 |

**开发时参考的官方文档（型号及字段会演进，不把当前表直接视为永久规范）：**

- OpenAI image generation: https://developers.openai.com/api/docs/guides/image-generation
- OpenAI Images API: https://developers.openai.com/api/reference/resources/images/methods/generate
- Gemini image generation: https://ai.google.dev/gemini-api/docs/image-generation
- Gemini `ImageConfig`: https://ai.google.dev/api/generate-content

**不确定能力的处理（P0）：**若只能证明接口接受 `auto`，却不能证明所选 2K/4K 会由该路由稳定得到原生相应档位，返回 `UNVERIFIED_NATIVE_TIER`；不允许收费生成后才把任意尺寸标注成目标档位。实际联网的能力探测应由用户明确触发或在合法、可控的验证流程内执行，不能暗中产生收费生图请求。

### 17.4 生成前预检与错误策略

| 检查 | 失败错误码 | 处理要求 |
| --- | --- | --- |
| 模型/路由不存在或未配置 | `MODEL_CAPABILITY_UNSUPPORTED` | 显示待配置型号，不擅自换服务商 |
| 所选档位明确不支持 | `UNSUPPORTED_RESOLUTION` | 显示该型号可用原生档位，等待用户另行选择 |
| 档位映射缺乏可靠来源或验证 | `UNVERIFIED_NATIVE_TIER` | 不调用付费生图接口；提示核验模型版本/能力档案 |
| 用户比例无法原生表达 | `UNSUPPORTED_RATIO` | 不自动转换为最接近的主流比例 |
| 图生图 / Sequence 的参考图能力不足 | `REFERENCE_REQUIRED` | 不降级为无参考图的独立生成 |
| 目标档位和比例不能**同时**满足 | `RESOLUTION_RATIO_COMBINATION_UNSUPPORTED` | 即使单独各自支持，也不能继续组合请求 |
| 能力未知但用户仍选择继续 | `CAPABILITY_CONFIRMATION_REQUIRED` | 需要用户做明确能力配置或试验授权；不得静默承诺质量 |

只有 `ready` 的 DimensionPlan 可以发送请求。报错必须包含 `requested_tier`、`requested_ratio`、`model_id`、`supported_options`（可知时）和简洁修复建议，不暴露 API Key、HTTP Authorization 或有敏感信息的原始请求。

### 17.5 Grid：原生作品板尺寸与可切图几何

1. **请求对象是整板**：生成调用只能请求一张 `N×N` 的作品板；`native_resolution_tier` 作用于整板，不能在返回的 Tile 上重复标注为「4K 单图」。
2. 按 `requested_aspect_ratio` 请求整板的画幅。正方网格 `N×N` 且每格宽高相等意味着整板和单格具有同一宽高比。此规则需被结果验证，而不靠 Prompt 自称合格。
3. 从模型响应中独立保存**未修改的原生返回尺寸** `raw_width`,`raw_height`；还可保存未修改原始文件供审计。
4. 原始画布宽高若不能被 N 整除，且网格结构视觉检验通过，可按第 7.2 节在每轴 ≤1% 的设计容差内对**副本**轻微几何规范化到 N 的倍数；记录新尺寸、差值、方法和源文件。不得借此拉伸错误比例或修复跨格错位。
5. 使用规范化作品板的整数等分坐标确定每个 Crop Box，所有 N² 张 Tile 应具有**严格相同的像素宽高**、顺序与 `crop_box`；不得出现间距、边框、跨格或缺格。
6. `board_original_native_resolution` 与 `tile_effective_dimensions` 必须分开记录。任何 Tile 清晰度不足，不能通过对该 Tile 插值放大来把结果宣称为原生 1K/2K/4K。
7. 质量检查分两层：**可机器确定**的尺寸、文件完整性、可整除、切图哈希/坐标；**视觉/模型辅助**的网格真实边界、主体一致性和格子差异性。只通过几何检查不代表网格实际可用。

**设计默认容差（需要真实模型验证后冻结）：**输出宽高比相对目标比误差 ≤1%；本地为可切图所作的单轴尺寸调整 ≤1%；这两个阈值分别检查，不能用一个抵消另一个。允许的微调须保留原图历史记录，且严禁补足缺失内容或强行拼格。

### 17.6 Sequence：每帧统一档位，但真实像素逐张验收

- 4–16 张 Sequence 中，所有帧请求**同一个原生 `resolution_tier` 和目标比例**，每一张独立调用模型和独立 Prompt；继续使用原图 / 第 1 帧一致性锚点，不改动第 8 章及 P1-07/P1-08 的主体约束。
- 每帧保存 `native_width`/`native_height` 和 `tier_verification`；同一个档位不保证所有 Provider 甚至某些型号在不同比例下的原生像素完全一致，但**同一次任务的每帧**必须满足同一型号当前能力档案所约定的档位规则。
- 如某一帧失败、比例不符或提供方返回非预期尺寸：只重试对应帧（在原重试上限内），不挪动序号、不静默降低档位、不以本地插值冒充合格帧。继续使用固定锚点而非逐帧接力。
- 对返回尺寸不完全一致的帧，只有在模型输出的合法尺寸变体和允许的几何容差内，才能另行产生展示副本；原生验证始终针对**原始返回图**。

### 17.7 生成后验收：不能只信请求参数

**至少同时满足：**

1. API 请求确实使用本次 DimensionPlan 的已验证原生映射；未降级、未改变用户比例/档位/模型。
2. 能解码实际图片；获取真实 `native_width`,`native_height`、格式和 SHA256；没有把响应文本、缩略图或后处理文件当作原始图片。
3. 原生像素与该型号 + 路由的**已声明预期或允许范围**一致。若 Provider 只有档位标签但无法提供固定尺寸表，则应检查模型返回的可用元数据和已验证尺寸范围；**不能凭请求成功就断言原生 4K 已验收通过**。
4. 目标比例在配置的有效容差内；不可使用后处理改变不合格原始比例来掩盖模型无能力。
5. Grid 通过严格可切图检查；Sequence 各帧完成、具有固定索引并保留锚点关系。
6. 结果中展示 `requested_tier`、`model_id`、`actual_native_width×height`。如原生档位验证失败，标记 `NATIVE_RESOLUTION_VALIDATION_FAILED`，不能标记为完整合格。

**禁止的伪验证：**「提示词包含 4K」「请求包含 high quality」「图片被 Photoshop 等比放大到了 4096×4096」「API 返回 HTTP 200」「整板可被 4 整除」均**不能单独**证明达到所选模型的原生 4K 档位。

### 17.8 Artifact / Manifest：新增可审计尺寸执行记录

原 `image-artifact.schema.json` 的 `schema_version=1.0` 和权威 `images[]` 结构继续可读；在旧 Manifest 顶层**增加兼容性字段 `dimension_execution`**，新发出的 v1.3 产物应写入该对象。Skill 02 保留原有引用机制，无须理解各厂商的参数细节，只读取最终被验证的单图真实尺寸及来源版本。

```json
{
  "dimension_execution": {
    "dimension_policy": "provider_native",
    "requested_tier": "2K",
    "requested_ratio": "3:4",
    "mapping_kind": "native_tier_parameter",
    "capability_profile_version": "PROFILE_REVISION",
    "provider_request_public": {"image_size": "2K", "aspect_ratio": "3:4"},
    "native_output": {"width": 1792, "height": 2400},
    "effective_output": {"width": 1791, "height": 2400},
    "geometry_adjustment": {"type": "minor_board_resample", "performed": true},
    "tier_validation": {"status": "passed", "method": "verified_profile_and_pixels"}
  }
}
```

这是**示例**，其 `native_output` 像素只是在特定型号和比例下可能出现的规格示意，不能复制为跨 Provider 的尺寸常量。对于 Sequence，可在 `dimension_execution.frames[]` 逐张记录原始尺寸和验证结果；对于 Grid，`native_output` 指**整板**，其 `effective_output` 用于后续切图坐标。存储接口调用参数时只能保留与尺寸相关的**白名单字段**，不能储存 Key、认证头、查询令牌或含密钥的 URL。

**强制的三类尺寸：**请求档位 `requested_tier`、模型原生实际尺寸 `native_output`、几何处理后实际尺寸 `effective_output`。切图另在既有 `images[]` 里记录每格 `width/height/crop_box`。这三个层次不能合并为一个 `resolution` 字段。

### 17.9 验收矩阵：模拟适配器 + 真实模型 + 两种宿主

| 编号 | 用例 | 必须验收的行为 |
| --- | --- | --- |
| DIM-01 | 2×2 Grid 无覆盖 | 仅向整板请求 1K，切出 4 张，Tile 不标原生 1K |
| DIM-02 | 3×3 Grid 无覆盖 | 整板 2K、9 等格、单图比例一致 |
| DIM-03 | 4×4 Grid 无覆盖 | 整板 4K、16 等格；模型无 4K 时预检明确报错 |
| DIM-04 | Sequence 默认 | 每张原生 1K，请求数 4–16，每帧记录真实像素 |
| DIM-05 | Sequence 指定 2K / 4K | 所有帧使用同一显式档位；单帧失败仅重试该帧 |
| DIM-06 | GPT Image 兼容 API | 根据选定型号/路由的已验证 `size` 映射；`quality` 不混同于 K 档 |
| DIM-07 | Gemini 兼容 API | 正确区分 `imageConfig.imageSize` 与 `response_format.image_size` 路由参数，并验证参数大小写 |
| DIM-08 | 任意参考图比例 | 精确继承逻辑比例；不支持则 `UNSUPPORTED_RATIO`；不可悄悄改 3:4 |
| DIM-09 | 目标比例 + 档位无法同时满足 | 不发出图像请求，报 `RESOLUTION_RATIO_COMBINATION_UNSUPPORTED` |
| DIM-10 | 只支持 1K 的模型请求 4K | `UNSUPPORTED_RESOLUTION`；无自动降级、无收费出图 |
| DIM-11 | 能力档案未知 | `UNVERIFIED_NATIVE_TIER`，不把 `auto` 当作 4K |
| DIM-12 | 生成返回像素与档案冲突 | 验收失败；记录原生像素，允许有限针对性重试 |
| DIM-13 | 3×3 非整除画板 | 仅在 ≤1% 调整且语义网格合格时规范化；原始尺寸留存 |
| DIM-14 | 4×4 主体跨格/白缝 | 即使尺寸可整除仍失败，不输出「已校验切图」 |
| DIM-15 | 用户/宿主两种安装来源 | 腾讯 WorkBuddy 桌面版与 DeepSeek Harness 均按相同规则执行预检和尺寸验证 |
| DIM-16 | 图片产物回溯 | Manifest 记录型号/档案版本/请求档位/原生像素/有效像素；API Key 不出现 |

**开发验收门槛：**先用 Mock Provider 覆盖 DIM-01～DIM-16 的通过和失败路径；再对至少一个实际 GPT Image 协议型号、一个实际 Gemini Nano Banana 型号和 WorkBuddy 宿主生图能力（若对该环境可用）做真实请求验证，记录 `model_id`、`api_route`、档案版本、输出样本和费用。所有无法实时核实的型号参数必须标注「待实测」，不得为了让测试通过直接写死推断的能力。

### 17.10 与 Prompt System、双 Skill 及公开仓库的关系

- 第 16 章 P1-01 解析用户的档位，P1-05/P1-07/P1-08 可以表达目标比例和档位，但**程序参数层是唯一的尺寸执行权威**；Prompt 不需要要求模型在画面上写 `4K` 等字样。
- Direction Rules 的主体一致性和视觉差异逻辑不因本次决策改变；所有 12 个方向继续支持 Grid / Sequence。
- Skill 02 的公众号封面可等比裁切/补边，但这是**内容衍生图**，不应宣称其改变了 Skill 01 的原生输出档位。
- 公开 Git 仓库保留**脱敏、可复现**的 Dimension Planner 示例和型号能力档案样本；真实 API Key 由安装用户在 WorkBuddy/DeepSeek Harness 本地解决，不能提交到 Git。宿主的内置生图工具能力若不可验证，则明确提示而非伪造 4K 支持。
- v1.2 前的 Manifest 可被兼容读取，新产物应填写 `dimension_execution`；如后续需要把其列为 Schema 必填，应通过新的 `schema_version` 和迁移测试完成，不能在不升级协议的情况下破坏旧产物读取。

### 17.11 尚需真实环境核验（不是未确认的产品决策）

1. 选定的 GPT Image **具体型号和路由**能接受哪些像素尺寸、边长与像素预算，以及产品档位到原生尺寸的配置映射。
2. 选定的 Gemini Nano Banana **具体型号和路由**能接受哪些枚举档位、比例和参考图格式；不同型号不能共享未经验证的能力档案。
3. WorkBuddy 桌面端是否公开对应生图工具的原生档位信息；若没有，是否只能按用户自配第三方 API 完成高分辨率任务。
4. 3×3 / 4×4 网格真实边界、像素微调容差与后续公众号封面裁切的质量表现。
5. 在 WorkBuddy 和 DeepSeek Harness 的真实安装环境中能否复现 Capability Profile 的预检与验收逻辑。

**以上五项不改变已经确认的 A 决策；它们是 Codex 开发阶段必须完成的提供方兼容性测试。**
